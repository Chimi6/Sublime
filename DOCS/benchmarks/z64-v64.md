# N64 ROM byte orders (z64, v64, n64)

**Latest** (2026-10-20, branch `n64`): every throughput line PASSES, at
1,450 to 2,090 MB/s against `dd conv=swab`'s 1,366 to 1,551,
`n64romconvert`'s 658 to 734, and ucon64's 460 to 588. The four memory
lines judged against ucon64 and `dd` (z64 <-> v64) FAIL by 0.1 to 0.6 MB:
2.6 MB against 2.0 to 2.1 and 2.3 to 2.5, from the binary's startup floor
(Threats to validity). Memory passes against `n64romconvert` everywhere.

## Purpose

The N64 ROM reorderer: a buffer read, each 32-bit word's bytes permuted
in place, the buffer written. It is a copy with a shuffle, so the pair
measures how close it runs to the copy and what the process costs around
it.

## Reference

`n64romconvert` 1.1.0, the Rust converter, every direction (compiled into
the bench binary). ucon64 2.2.2 (Homebrew), the long-standing ROM tool:
`--v64` and `--z64` (it does not know little-endian n64). `dd
conv=swab` (macOS), which swaps byte pairs, so z64 <-> v64. Implemented
in `bench/pairs/z64-v64.sh` and `bench/src/pairs/z64_v64.rs`.

Every reference's output is compared with ours byte for byte in every
run; all were identical on both inputs, in every direction each supports.

## Pass lines

Not slower, and no more memory, than every reference that does the
direction. Throughput is MB/s of input.

## Method

**Machine.** Recorded with each results block.

**Inputs.** Generated: 64 MB, the largest cartridge, of pseudo-random
words behind a big-endian header (`sublime-bench z64-v64 gen`). Real:
Paper Mario (USA), 40 MB, a No-Intro dump (`$SUBLIME_N64_ROM`, not
distributed). The v64 and n64 inputs are ours from the z64, checked
against the crate's in the run, and flushed to disk (`sync`) before any
timing.

**Statistics.** `bench/run.sh z64-v64`: each command timed 15 times (a
conversion takes 20 to 50 ms, so three runs were noise; `bench_runs`),
median wall clock of the whole process, peak resident memory from GNU
`time`.

**Commands.**

- ours: `sublime -q convert in.z64 out.v64` (and each direction)
- n64romconvert: `sublime-bench z64-v64 crate z64-v64 in.z64 out.v64`
- ucon64: `ucon64 --nbak --v64 rom.z64` in a scratch folder
- dd: `dd if=in.z64 bs=1048576 conv=swab status=none of=out.v64`

## How it got here

- The first kernel loaded each word as a `u32`, permuted it with shifts
  and masks, and stored it: 11 ms of user time on 64 MB, scalar. Written
  as an array shuffle (`[w[1], w[0], w[3], w[2]]`), the compiler
  vectorizes it: 3 ms. `dd`'s byte-pair loop is 13 ms.
- Buffer size, measured standalone on 64 MB: 1 MB 20.1 ms of CPU at
  2.34 MB peak, 256 KB 21.4 ms at 1.59 MB, 64 KB 26.7 ms at 1.41 MB.
  256 KB costs about a millisecond and saves 0.75 MB.
- The first recorded run had the first row at 763 MB/s (FAIL against
  `dd`), and a rerun at 1,078: the 128 MB of v64 and n64 inputs written
  just before were still going to disk while ours, the first command, was
  timed. The script now runs `sync` after making them; that row is
  1,783 to 2,090 since.

## Threats to validity

- **The memory lines.** The binary holds 2.24 MB before it reads a byte
  (`sublime check z64 v64`, which plans and exits), against ucon64's 2.0
  for its whole conversion: the code pages that loading the converter
  registry and planning touch (about 800 KB of the program's code is
  resident; `--version` alone is 1.68 MB). No buffer size passes these
  lines; a registry held as data rather than reached through each
  converter's methods would lower every conversion's floor, and is left
  for the binary-wide work.
- ucon64 does more than convert: it reports the header and checks the
  checksums, as it does on every run.
- `dd conv=swab` only swaps pairs; it is a floor for the z64 <-> v64 copy,
  not an N64 tool.
- `n64romconvert` reads through a `BufReader` 512 bytes or 1 KB at a time
  and writes each chunk whole even when a read returns fewer bytes; on these inputs
  every read was full and its outputs matched.
