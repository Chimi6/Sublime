# YAML <-> JSON

**Latest** (2026-09-25, arena tree: yaml -> json 128.9 MB/s of input on the dense shape and 322.6 on prose, at 235 and 427 MB peak; json -> yaml 98.5 and 356.0 MB/s at 172 and 211 MB peak; every line PASSES against serde_yaml with serde_json, at 2.3 to 5 times its throughput and 11 to 49 percent of its memory)

## Purpose

The second tree-shaped data pair on the value hub, and the format people
convert most: YAML to JSON for tooling and validation, JSON to YAML for
configuration people will read. The reader is the largest grammar in the
data category (block structure by indentation, five scalar styles,
anchors, merge keys), so this pair is where its cost per byte is known.

## Reference

`serde_yaml` (version 0.9, the YAML crate Rust programs have reached for
by default; unmaintained since 2024 but still the most used) with
`serde_json`: `serde_yaml::from_reader` into a `serde_yaml::Value` then
`serde_json::to_writer` (YAML to JSON), and `serde_json::from_reader`
into a `serde_json::Value` then `serde_yaml::to_writer` (JSON to YAML).
Implemented in `bench/src/pairs/yaml_json.rs`.

## Pass lines

Not slower, and no more memory, than `serde_yaml` with `serde_json`, in
each direction and on each shape.

## Method

**Machine.** Recorded with each results block from the harness's
machine line.

**Inputs.** Generated by `bench/src/pairs/yaml_json.rs`, capped at
300,000 units. `dense`: a sequence of mappings, each a record of ten
members (integer, plain and quoted strings, float, boolean, datetime as
a plain scalar, flow sequence, nested mapping); 62.3 MB of YAML and 56.2
MB of the same records as JSON. `prose`: one mapping per unit holding a
heading, a literal block scalar of four to eight generated sentence
lines, and a word count; 190.1 MB of YAML and 180.0 MB of JSON. The JSON
files are generated directly, not converted, so the two directions are
independent.

**Statistics.** `bench/run.sh yaml-json`: three runs per command, median
wall clock of the whole process, peak resident memory from GNU `time`,
throughput in MB/s over the input file's bytes. Rows and units follow
`README.md`.

**Commands.** Per shape:

- ours: `sublime -q convert big.yaml out.json` and `sublime -q convert big.json out.yaml`
- reference: `sublime-bench yaml-json crates-yaml-json big.yaml out.json` and `crates-json-yaml big.json out.yaml`

## Threats to validity

- Real YAML is small (a config file, a pipeline definition); the inputs
  are inflated so the numbers are measurable, and both pipelines build
  the whole tree, so the memory rows say what a tree costs per byte.
- The dense records use plain scalars almost everywhere and no anchors;
  a document of many aliases costs ours a copy per alias, which these
  inputs do not exercise.
- The prose shape is one literal block per record, the cheapest scalar
  style to read; folded blocks and multi-line plain scalars do more
  work per line.
- `serde_yaml` runs on libyaml's grammar through a Rust port; its numbers
  say what an event-stream parser plus a generic tree costs, not that it
  is slow at what it does.

## Conclusions

The reader is five times the reference on the dense shape and the tree
costs about three bytes per input byte. The json -> yaml dense
throughput (98.5 MB/s, the lowest row) is the writer's plain-safety
check, which resolves every string through the core schema before
writing it plain; a byte-class prefilter would skip most of that. The
yaml -> json rows hold the input text beside the tree (62 and 190 MB of
their peaks); a windowed reader like XML's is the lever if a large YAML
case ever matters. The numbers do not justify claims about alias-heavy
or deeply nested documents.
