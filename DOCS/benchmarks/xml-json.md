# XML <-> JSON

**Latest** (2026-09-24, first release of XML: xml -> json 103.8 MB/s of input on the dense shape and 402.0 on prose, at 570 and 310 MB peak; json -> xml 84.6 and 345.8 MB/s at 588 and 310 MB peak; every line PASSES against quick-xml with serde_json, at 1.1 to 1.6 times its throughput and 73 to 95 percent of its memory)

## Purpose

The third tree-shaped data pair on the value hub and the first whose
input is large in practice: XML is exports, feeds, and configuration
alike, so the reader streams its input where TOML's and YAML's read it
whole. The pair measures the strict tokenizer and the xmltodict mapping
in both directions.

## Reference

`quick-xml` (the fast XML crate Rust programs reach for) with
`serde_json`, doing the same mapping by hand: quick-xml's event reader
building a `serde_json` tree with attributes as `@name`, text as
`#text`, and repeated elements as arrays (XML to JSON); `serde_json`
into quick-xml's indenting writer (JSON to XML). The mapping is written
out in the harness rather than taken from quick-xml's serde support, so
both sides do the same work. Implemented in
`bench/src/pairs/xml_json.rs`. `xmltodict` (Python) is the other
conventional tool for this mapping and is not wired in.

## Pass lines

Not slower, and no more memory, than quick-xml with serde_json, in each
direction and on each shape.

## Method

**Machine.** Recorded with each results block from the harness's
machine line.

**Inputs.** Generated by `bench/src/pairs/xml_json.rs`, capped at
300,000 units. `dense`: a list of `record` elements with two attributes
and eight short children (two of them a repeated `tag`, one an
attribute-only `limits`); 80.0 MB of XML and 58.2 MB of the mapped JSON.
`prose`: `section` elements holding a heading, a paragraph of four to
eight generated sentences as text, and a word count; 194.4 MB of XML and
180.6 MB of JSON. The JSON files are generated directly, not converted,
so the two directions are independent.

**Statistics.** `bench/run.sh xml-json`: three runs per command, median
wall clock of the whole process, peak resident memory from GNU `time`,
throughput in MB/s over the input file's bytes. Rows and units follow
`README.md`.

**Commands.** Per shape:

- ours: `sublime -q convert big.xml out.json` and `sublime -q convert big.json out.xml`
- reference: `sublime-bench xml-json crates-xml-json big.xml out.json` and `crates-json-xml big.json out.xml`

## Threats to validity

- The inputs are machine-written and regular: no namespaces, no CDATA,
  few entities, no mixed content, indentation whitespace between every
  element. A document of long attribute lists or deeply nested small
  elements spends its time differently.
- Both pipelines build the whole tree, so the memory rows say what a
  tree costs per byte; ours streams the input and quick-xml reads it
  through a buffer, so neither holds the file.
- The reference mapping is our own code over quick-xml's events; a
  different choice there (a `BTreeMap` versus `IndexMap` tree, trimming
  rules) moves its numbers.

The first run, with the reader holding the whole input beside the
tree, failed three xml -> json rows (650 against 604 MB dense, 505
against 427 MB prose, and 338 against 349 MB/s on prose). Pulling the
input through a 256 KiB window fixed the memory rows and cost
throughput; scanning text, names, and whitespace a word at a time over
the window and removing three allocations per element (the end-tag name,
the pending text copy, the newline normalization copy) is what the block
above measures.

## Conclusions

The reader streams, so what a document costs is its tree: 570 MB for
80 MB of dense records, seven bytes per input byte, and the arena-backed
tree in `STATE.md` Tech Debt is the lever shared with TOML and YAML. The
narrowest margin is json -> xml dense (84.6 against 76.5 MB/s), where
the writer builds a scratch string per attribute and per text node
before escaping; escaping straight into the chunked sink would take
that back. The numbers do not justify claims about namespace-heavy,
mixed-content, or deeply nested documents.
