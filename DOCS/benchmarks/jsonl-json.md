# JSON Lines <-> JSON

**Latest** (2026-10-21, 1.0.0 release run: jsonl -> json 187.6 MB/s of input at 2.7 MB peak; json -> jsonl 193.6 MB/s at 2.7 MB peak; every line PASSES against serde_json, at 1.9 to 3.1 times its throughput)

## Purpose

JSON Lines is one JSON value per line; the pair measures the token
copier (`io::json::copy`) that turns lines into an array and back
without building a tree, which is also the path CSV and TSV take to and
from JSON Lines through the row converters.

## Reference

`serde_json`'s stream deserializer (`Deserializer::into_iter::<Value>`)
into a streaming sequence serializer (JSON Lines to JSON), and
`serde_json::from_reader` into a `Vec<Value>` written one value per line
(JSON to JSON Lines). The first streams as ours does; the second holds
the array, as `serde_json` has no streaming array reader. Implemented in
`bench/src/pairs/jsonl_json.rs`.

## Pass lines

Not slower, and no more memory, than `serde_json`, in each direction.

## Method

**Machine.** Recorded with each results block from the harness's
machine line.

**Inputs.** Generated by `bench/src/pairs/jsonl_json.rs`: 10,000,000
records with an integer, four strings, a nested array, and a note, one
per line (1,234.6 MB), and the same records as one array written by our
own `jsonl -> json` (1,234.6 MB).

**Statistics.** `bench/run.sh jsonl-json`: three runs per command,
median wall clock of the whole process, peak resident memory from GNU
`time`, throughput in MB/s over the input file's bytes. Rows and units
follow `README.md`.

**Commands.**

- ours: `sublime -q convert big.jsonl out.json` and `sublime -q convert big-lines.json out.jsonl`
- reference: `sublime-bench jsonl-json crates-jsonl-json big.jsonl out.json` and `crates-json-jsonl big-lines.json out.jsonl`

## Threats to validity

- The reference JSON-to-JSON-Lines pipeline holds the whole array; its
  memory row is that choice, not a limit of `serde_json`, which could
  stream with a custom visitor.
- The records are regular and shallow (one nested array); deep nesting
  costs both sides recursion and neither more than the other.

## Results

### 2026-10-21, `v1-wrapup` branch, the 1.0.0 release run

commit: ec68950
machine: Darwin 24.5.0 arm64, 10 cpus, Apple M1 Max

| Target | Ours | Reference | Result |
|---|---|---|---|
| jsonl -> json, 10M rows (1234.6 MB): throughput (MB/s of input) | 187.6 | 99.3 (serde_json) | PASS |
| jsonl -> json, 10M rows: peak memory (MB) | 2.7 | 5.1 (serde_json) | PASS |
| json -> jsonl, 10M rows (1234.6 MB): throughput (MB/s of input) | 193.6 | 61.6 (serde_json) | PASS |
| json -> jsonl, 10M rows: peak memory (MB) | 2.7 | 7884.5 (serde_json) | PASS |

Every line passes, at 1.9 and 3.1 times serde_json's throughput. This
run is on a different machine from the previous block (an M1 Max, not
the Linux i7-13700K), so its absolute MB/s do not compare with that
block's; the ratios against the reference in the same session do. The
machine was in use during the run (load average 7 to 12 on 10 cores: a
browser, a VPN client, a remote-desktop host), so the wall-clock rows
are noisier than earlier blocks'.

## Conclusions

The token copier runs at the tokenizer's pace in both directions and
holds one value at a time. Nothing here is close to a limit; the
tokenizer's string scan is the shared cost with every JSON pair.
