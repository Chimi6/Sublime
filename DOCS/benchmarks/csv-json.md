# CSV <-> JSON

**Latest** (2026-09-23, 0.3.0: csv -> json 333 MB/s of input, 2.4 MB peak; json -> csv 191 MB/s, 2.4 MB peak; all lines PASS against the csv and serde_json crates)

## Purpose

The first native pair and the hello world of the framework. CSV to JSON is
the most common tabular conversion people reach for a script to do; JSON to
CSV is its inverse and the first two-pass converter. This pair is where the
zero-dependency parsers were first proven against the conventional crates.

## Pass lines

| Target | Pass line |
|---|---|
| CSV -> JSON throughput | >= the `csv` crate reading records into a streaming `serde_json` map serializer |
| JSON -> CSV throughput, file input | >= `serde_json` into the `csv` writer |
| Peak resident memory at 1 GB input, file source, both directions | < 16 MB |
| Peak resident memory at 1 GB input, stdin source, CSV -> JSON | < 16 MB |
| Release binary size, Linux x86_64 musl static | < 1 MB |
| Startup to first byte of output on a 1 KB file, above the process-spawn floor | < 1 ms |

## Method

**Machine.** Linux x86_64, 24 CPUs, 31 GB RAM, NVMe. Recorded on each
results block as printed by the harness.

**Inputs.** Generated by `bench/src/pairs/csv_json.rs`. Rows have six
fields: `id,name,email,city,score,note`. Every seventh row's `note` is a
quoted field containing a comma. Field values are short, mostly under eight
bytes. The full run uses 10,000,000 rows, about 1.18 GB of CSV and a matching
JSON array of objects with string values. The JSON file is generated
directly, not converted from the CSV, so the two directions are independent.

**Commands.** `bench/run.sh csv-json` builds both crates in release, generates
inputs if absent, and runs:

- ours: `sublime -q convert big.csv out.json` and `sublime -q convert big.json out.csv`
- reference: `sublime-bench csv-json crates-csv-json` and `crates-json-csv`
- stdin memory: `sublime -q convert - --from csv --to json < big.csv`

**Statistics.** Each timed pipeline runs three times; the median wall-clock
time is reported as throughput in MB/s over the input size. Peak resident
memory is the maximum resident set size from GNU `time`. Binary size is the
musl static release build when the target is installed, otherwise the glibc
build, and the table says which.

**Startup.** Timed inside the bench binary with `Instant`, from `spawn` to
the first byte of stdout, median of 25 runs, for `sublime convert tiny.csv
--to json` on a two-row file. The process-spawn floor is the same
measurement for `/bin/true`. The pass line applies to the difference, which
is the part attributable to the binary. Shell-based timing forks extra
processes per sample and cannot resolve sub-millisecond startups.

**Reference pipelines.** In `bench/src/pairs/csv_json.rs`. CSV to JSON:
`csv::Reader` streaming `StringRecord`s into `serde_json::Serializer` through
`SerializeSeq` and a map serializer per record, no `Value` tree. JSON to CSV:
`serde_json::from_reader` into `Vec<Value>`, ordered key union, then
`csv::Writer`. The JSON to CSV reference builds a tree, which is the
conventional way and part of what the comparison measures.

**Reader-only modes.** `ours-csv-read` and `crates-csv-read` read every
record and discard it, to separate parser cost from writer cost.

## Threats to validity

- One synthetic shape. Short fields with few quotes flatter per-field
  overhead and say nothing about wide rows, long quoted text, embedded
  newlines, or Unicode-heavy data.
- Page cache. Inputs are read from cache after generation; cold reads would
  be dominated by disk for both sides.
- CPU power state. Startup medians were bimodal across repeats, and so was
  the `/bin/true` floor, which is why startup is reported as a range and
  above the floor.
- One machine. Ratios should transfer; absolute MB/s will not.
- Reference choices. The CSV to JSON reference is a fair streaming pipeline.
  The JSON to CSV reference builds a `Value` tree because that is the
  conventional way; a hand-written streaming reference would be faster.

## Conclusions

- The first spike found the bottleneck in the JSON writer, not the CSV
  reader: about thirty virtual write calls per row. Buffering inside the
  writer was the single largest win. The word-at-a-time scanner in
  `io::scan` and pre-escaped header keys closed the rest.
- The CSV reader alone is still about 40% slower than the `csv` crate's
  reader. The end-to-end win comes from skipping intermediate representation,
  not from a faster parser. A SIMD scanner remains the stretch target.
- These numbers justify "faster end to end than the conventional Rust
  pipeline on this input shape". They do not justify a general claim until a
  second input shape (wide rows, long quoted text, Unicode) is measured.
- JSON to CSV from stdin buffers the whole input once; the 3.4 MB stdin
  figure is for CSV to JSON. Measuring JSON to CSV from stdin is a gap.
