# TOML <-> JSON

**Latest** (2026-09-25, arena tree: toml -> json 148.2 MB/s of input on the dense shape and 323.5 on prose, at 237 and 421 MB peak; json -> toml 156.7 and 309.2 MB/s at 172 and 212 MB peak; every line PASSES against the `toml` crate with `serde_json`, at 1.9 to 3.7 times its throughput and 12 to 47 percent of its memory)

## Purpose

The first tree-shaped data pair and the first user of the value hub
(`src/value`). TOML to JSON is the config conversion people reach for a
script to do; JSON to TOML is its inverse and the first writer that must
lay a tree out under headers. This pair is where the hub's cost is
measured before YAML and XML share it.

## Reference

The `toml` crate (the Rust TOML parser and serializer, version 1) with
`serde_json`: `toml::from_str` into a `toml::Table` then
`serde_json::to_writer` (TOML to JSON), and `serde_json::from_reader`
into a `toml::Table` then `toml::to_string` (JSON to TOML). These are the
crates a Rust programmer reaches for by default, so the numbers stand
against the conventional pipeline. Implemented in
`bench/src/pairs/toml_json.rs`.

## Pass lines

Not slower, and no more memory, than the `toml` crate with `serde_json`,
in each direction and on each shape.

## Method

**Machine.** Recorded with each results block from the harness's
machine line.

**Inputs.** Generated by `bench/src/pairs/toml_json.rs`, capped at
300,000 units. `dense`: an array of tables (`[[record]]`), each a record
of ten members (integer, strings with the odd escape, float, boolean,
offset datetime, inline array, inline table); 59.9 MB of TOML and 56.2
MB of the same records as a JSON object. `prose`: one `[section.sN]`
header table per unit holding a heading, a multi-line basic string of
four to eight generated sentences, and a word count; 182.0 MB of TOML
and 178.9 MB of JSON. The JSON files are generated directly, not
converted, so the two directions are independent.

**Statistics.** `bench/run.sh toml-json`: three runs per command, median
wall clock of the whole process, peak resident memory from GNU `time`,
throughput in MB/s over the input file's bytes. Rows and units follow
`README.md`.

**Commands.** Per shape:

- ours: `sublime -q convert big.toml out.json` and `sublime -q convert big.json out.toml`
- reference: `sublime-bench toml-json crates-toml-json big.toml out.json` and `crates-json-toml big.json out.toml`

## Threats to validity

- Real TOML is small (a config file); the inputs are inflated so the
  numbers are measurable. Both pipelines build the whole tree, so the
  memory rows say what a tree costs per byte, which a config file never
  feels.
- The dense records are regular: short keys, few string escapes, no
  multi-line strings. Odd documents (deep nesting, long dotted keys,
  many small inline tables) spend more time in table lookups.
- `toml` datetimes serialize through `serde_json` as a one-member map,
  not a string, so the reference writes a little more JSON than ours on
  the dense shape.
- Peak memory for ours includes the output held as one string before
  the write (JSON to TOML) and the input held whole (TOML to JSON).

prose toml -> json row still holds the input text (182 MB) beside the
tree; the reader borrows it, so that is the floor for that row.

## Conclusions

The reader and writer are ahead of the reference on every row. With the
arena the dense shape costs about three bytes of tree per input byte
(a node is 32 bytes and a string its bytes), and the parse is faster
because nothing is allocated per value. What remains on the dense rows
is the input text held whole by the reader (60 MB of the 237) and the
JSON writer's per-key escaping; on prose it is the input text (182 MB of
the 421). A windowed reader like XML's would take the input out of the
peak if a large TOML case ever matters. The numbers do not justify
claiming anything about deeply nested documents or pathological key
sets, which the inputs do not have.
