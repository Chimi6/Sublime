# Markdown -> HTML

**Latest** (2026-09-23, 0.2.0: markdown -> html 118 MB/s of input on the markup-dense shape and 370 MB/s on prose, at 304 and 83 MB peak; all lines PASS against pulldown-cmark)

## Purpose

The first document-shaped pair and the first full parser in the project.
Markdown is small and ubiquitous, so absolute throughput matters less than
for tabular data, but the parser is the shared front end for every future
Markdown path (plain text, JSON, PDF), so its cost is paid everywhere.

## Reference

`pulldown-cmark` 0.13 with the same extension set (tables, footnotes,
strikethrough, task lists, GFM autolinks), rendered by its own HTML writer. It
is the de facto Rust CommonMark and GFM implementation, the one every Markdown
tool is measured against, so it is the fair peer for this path. Implemented in
`bench/src/pairs/markdown_html.rs`.

## Pass lines

| Target | Pass line |
|---|---|
| Markdown -> HTML throughput | >= `pulldown-cmark` with tables, footnotes, strikethrough, task lists, and GFM autolinks, rendered by its own HTML writer |
| Peak resident memory | <= the same reference on the same input |
| Release binary size, Linux x86_64 musl static | recorded; the CI budget is the gate |
| Startup above the process-spawn floor | < 1 ms (binary-wide) |

## Method

**Machine.** Linux x86_64, 24 CPUs, 31 GB RAM, NVMe, as printed by the
harness on each results block.

**Inputs.** Two documents generated by `bench/src/pairs/markdown_html.rs`.

- *Markup-dense.* Each unit is about 1.1 KB and exercises a heading, a
  paragraph with emphasis, strong, code spans, an inline link with a title,
  an angle-bracket autolink, an entity, and strikethrough; a bullet list
  with a nested item and a task item; an ordered list; a two-line block
  quote; a fenced code block; a three-column table with alignments; and
  literal autolinks. One unit in twenty also carries a footnote reference,
  a reference-style link, and their definitions. The full run uses 100,000
  units, about 86 MB.
- *Prose.* Each unit is a five-line paragraph of plain sentences with one
  emphasis, one link, and one code span, a heading before every eighth
  paragraph, and a three-item list after every fifth. About 0.6 KB per
  unit; 100,000 units, about 59 MB. Most real documents are closer to this
  shape than to the dense one, so tuning is checked against both.

**Commands.** `bench/run.sh markdown-html` builds both crates in release,
generates the input if absent, and runs:

- ours: `sublime -q convert big.md out.html` (and the same for `prose.md`)
- reference: `sublime-bench markdown-html crates big.md out.html`

`sublime-bench markdown-html phases <file>` times the pipeline in-process
(block structure, inline parsing, full render, and the reference) without
process start or file I/O; the numbers below that are marked in-process
come from it.

**Statistics.** Three runs each; the median wall-clock time is reported as
throughput in MB/s over the input size. Peak resident memory is the maximum
resident set size from GNU `time`. Binary size and startup are measured the
same way as for every pair (see `csv-json.md`).

**Reference pipeline.** `pulldown-cmark` 0.13 with `ENABLE_TABLES`,
`ENABLE_FOOTNOTES`, `ENABLE_STRIKETHROUGH`, `ENABLE_TASKLISTS`, and
`ENABLE_GFM`, parsing a `String` read from the file and rendering with
`pulldown_cmark::html::push_html` into a `String` written once. That is the
conventional way to use the crate and holds input and output in memory, as
our converter holds the input and the block tree.

**Correctness baseline.** Both implementations are held to the same
specification corpora; ours runs all 652 CommonMark examples, the GFM
extension examples, and cmark-gfm's extension examples in CI. On the prose
input the two outputs are byte-identical. On the dense input they are not
compared byte for byte, because footnote and task list markup legitimately
differ between renderers.

## Threats to validity

- Two synthetic shapes with fixed construct mixes. The dense input weighs
  the block parser (lists, tables, code); the prose input weighs the inline
  parser and the writer. Neither has long runs of raw HTML, deeply nested
  quotes, or pathological emphasis.
- Footnote density. A definition per unit made both implementations
  quadratic in the number of footnotes (observed: minutes instead of
  seconds on 100,000 units). Our footnote lookup is now constant time; the
  generator uses one definition per twenty units, which is still 5,000
  footnotes in the full dense run and enough to dominate the reference's
  time. The dense comparison is therefore also reported at 20,000 units
  (1,000 footnotes), where the reference is not yet quadratic.
- Page cache and CPU power state, as for every pair.
- Reference choices. `ENABLE_GFM` in `pulldown-cmark` also changes some
  rendering details; the extension set is the closest match to ours, not an
  identical one.

## Results

2026-09-23, working tree after `d22f8b2` (release build, glibc, `-C
target-cpu` default). Full run, medians of three:

| Target | Ours | Reference | Result |
|---|---|---|---|
| Markdown -> HTML throughput, markup-dense, 100,000 units (MB/s) | 117.9 | 4.2 | PASS |
| Markdown -> HTML throughput, prose, 100,000 units (MB/s) | 370.2 | 293.1 | PASS |
| Peak RSS, markup-dense (MB) | 303.8 | 696.3 | PASS |
| Peak RSS, prose (MB) | 83.0 | 231.4 | PASS |
| Binary size, musl static (bytes) | 852,608 | < 1,048,576 | PASS |
| Startup above spawn floor (ms, 1 KB file) | 0.67 | < 1 | PASS |

Dense input at 20,000 units (14.6 MB, 1,000 footnotes), where the
reference's footnote cost is not yet quadratic; eight runs each,
interleaved, wall clock:

| | Ours | Reference |
|---|---|---|
| End to end, min / median (ms) | 119 / 123 | 119 / 121 |
| In-process parse and render (ms) | 94 | 95 |
| Peak RSS (MB) | 63 | 144 |

Prose input at 25,000 units (14.8 MB), same method:

| | Ours | Reference |
|---|---|---|
| End to end, min / median (ms) | 36 / 40 | 48 / 53 |
| In-process parse and render (ms) | 25 | 31 |
| Peak RSS (MB) | 23 | 61 |

Where the time went, from stack sampling of the converter process on the
dense input (`eu-stack`, about 2,000 samples): block structure 30%, inline
parsing 21%, HTML writing 17%, file read and write 11%, allocation 7%. The
single hottest instructions were first stores into freshly grown arenas
(page faults and cache misses on new memory), not any parsing logic.

**Size cost.** The Markdown subsystem (parser, entity table, HTML writer,
converter) added about 200 KB to the release binary: 555 KB at 0.1.0 to
756 KB now (glibc build; the size budget gate uses this number).

## Conclusions

- The pass lines hold on both inputs. On prose, the shape most documents
  have, we are about a quarter faster than the reference end to end and
  use less than half the memory. On markup-dense text we are level in
  process (94 ms vs 95 ms on 14.6 MB) and within noise end to end, at 2.3
  times less memory.
- The reference's footnote handling is quadratic; at 5,000 footnotes it is
  28 times slower than ours. That is a real advantage on long academic
  documents but says nothing about parser speed, which is why the dense
  comparison is also reported at a smaller size.
- Three changes made the difference after the parser was correct: pushing
  events straight into the writer instead of buffering them per block (the
  buffer round trip cost more than rendering), borrowing text from the
  source at every stage (block lines, inline nodes, autolink pieces), and
  fixing a store-forwarding stall in the shared byte scanner's tail load
  that hit every short text run in every converter.
- The remaining gap to a clear lead on dense input is memory traffic, not
  logic: first-touch page faults in the node and line arenas. Shrinking
  those records is the next spike (see `DOCS/STATE.md`).
