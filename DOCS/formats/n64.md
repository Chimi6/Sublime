# N64 ROMs (z64, v64, n64)

A Nintendo 64 cartridge dump is the cartridge's bytes, and the console
reads them as big-endian 32-bit words. Dumps come in three byte orders,
the same bytes placed differently within each word:

| Id | Order | Bytes of a word | Came from |
|---|---|---|---|
| `z64` | big-endian, as the console reads it | 1 2 3 4 | Mr. Backup Z64; the order No-Intro's checksums are of |
| `v64` | each 16-bit pair swapped | 2 1 4 3 | Doctor V64 |
| `n64` | each word reversed (little-endian) | 4 3 2 1 | some PC tools and emulators |

Sublime converts between all three (`src/io/n64.rs`,
`src/converters/n64.rs`). Every byte is kept, so each conversion is
lossless, and a ROM converted there and back is the same file.

## Status

- `z64`, `v64`, `n64`, each to the other two: shipped, lossless.

Checked on Paper Mario (USA), a 40 MB No-Intro dump (not distributed):
z64 to v64 to z64 and z64 to n64 to z64 come back to its SHA-1, and both
routes to each order give the same bytes. Our v64 is byte-identical to
ucon64's; ucon64 reads it as a Doctor V64 dump with both header checksums
OK. Our v64 and n64 are byte-identical to `n64romconvert`'s and v64 to
`dd conv=swab`'s, on that ROM and on a generated 64 MB one (pair
`z64-v64`).

The user played the converted ROMs in an emulator in every order
(2026-10-20); there is no automated boot test (mupen64plus prints
nothing headless here), so byte identity stands in.

Oracles: `tests/n64.rs` makes a 3 MB ROM (more than the converter's
buffer) and writes each order by index, apart from the converter's own
code, then checks every conversion against them through the binary; a
byte-swapped ROM named `.z64` read by its header, by `--from`, and in batch
mode; standard input; a ROM of part words refused with nothing written.
`src/io/n64.rs` checks the header rule and reads that hand out a few bytes
at a time. The wasm smoke test converts a ROM in the browser module.

## The order is read from the header

The header's first word is the cartridge's bus configuration,
`0x80371240` on almost every cartridge, with `0x80` in its first byte on
all of them. Where that byte lies tells the order (byte 1 for `z64`, 2
for `v64`, 4 for `n64`), so a file is read in the order its header shows,
whatever it is named. This matters because the extensions are used
loosely, `.n64` above all.

- **Named for another order.** Read in the order the header shows, with a
  warning naming both. The command line goes further: a file whose
  extension's signature it fails and another's it matches is read as that
  format, so a byte-swapped ROM saved as `game.z64` becomes a big-endian
  `fixed.z64` (`sublime convert game.z64 fixed.z64`) rather than stopping
  at "same format". This applies to every format with a signature.
- **Already in the target order.** Copied unchanged, with a warning.
- **Not a ROM header.** Read in the order the name gives, with a warning;
  the bytes are reordered all the same.
- **Not whole words.** Refused (`an N64 ROM is whole 32-bit words`), and
  no output is left behind. Fewer than four bytes are refused too.

The header's checksums are computed over big-endian words, so they are
the same in every order and nothing in the ROM is rewritten.

## Performance

Streamed through a 256 KB buffer reordered in place, with the shuffle
written so the compiler vectorizes it. About 1,750 MB/s on an M1 Max:
1.2 to 1.35 times `dd conv=swab`, 2.2 to 2.9 times `n64romconvert`, and
3 to 4.2 times ucon64. Memory is the binary's startup floor plus the buffer
(2.6 MB), a little over ucon64's 2.0 and `dd`'s 2.3.
`DOCS/benchmarks/z64-v64.md`.

## Not covered

Copier headers (a 512-byte header some old dumps carry in front of the
ROM), 64DD disk images (`.ndd`), save files (EEPROM, SRAM, FlashRAM,
Controller Pak), and repairing header checksums are not handled.
